# S40 Data Strategy

Phase 3 deliverable. Governs how S40 acquires, represents, validates and
splits data for its independent detectors.

Status labels used throughout: **CONFIRMED**, **PROPOSED**, **UNDECIDED**,
**PENDING LICENCE VERIFICATION**, **FUTURE PHASE**.

Companion documents: `docs/ML_ARCHITECTURE.md` (model design),
`docs/SECURITY.md` (privacy), `docs/DEVELOPMENT_PLAN.md` (phasing).

---

## 1. Strategy in one paragraph

S40 uses a **hybrid, multi-source** strategy: several public datasets, each
scoped to the specific detector it can honestly inform, plus an in-repo
synthetic generator for the India/UPI scenarios no public dataset contains.
Datasets are **never concatenated into one training set**. Each is mapped
through an adapter into a canonical representation that records *which
concepts that dataset actually observes*, so a missing concept stays
missing rather than being quietly invented.

### 2.1 PaySim — PARTIALLY VERIFIED
Source: <https://www.kaggle.com/datasets/ealaxi/paysim1>.
Generated by the PaySim simulator (Dr. Edgar Lopez-Rojas; *PaySim: A
financial mobile money simulator for fraud detection*, EMSS 2016). The
simulator is seeded from **aggregated** logs of a real African
mobile-money service; published rows are simulator output, **not real
customer records**.

GPL-3.0 on the simulator source was confirmed from the author's GitHub
repository. The licence on the **Kaggle CSV** could not be read: Kaggle
serves a JavaScript application, so the licence field is absent from
fetched HTML. It is widely cited as CC BY-SA 4.0, but that is **unconfirmed
here**. *Action: a human must check the dataset page before any public
submission.*

### 2.2 IEEE-CIS — PENDING LICENCE VERIFICATION

The rules page could not be read programmatically. Kaggle competition data

Source: <https://huggingface.co/datasets/JimmyMa99/TeleAntiFraud>.
Licence: **Apache-2.0** (copyright Zhiming Ma, 2025) — commercial and

### 2.5 S40 synthetic — project-owned
`ml/data/generators/synthetic_generator.py`. No external data, no real
people. See §7.

### 2.6 Rules for all external data
- **Never committed to Git.** `.gitignore` excludes `ml/data/raw/`,
  `processed/`, `synthetic/` and large columnar formats.
- **Never redistributed** through this repository.
- Test fixtures in `ml/tests/fixtures/` are **hand-authored**, not
  excerpts — see that directory's README.
- Never described as "real banking data" unless the source supports it
  (only IEEE-CIS and ULB are real-world; both are flagged in the registry).

## 3. Canonical representation — CONFIRMED

Two **separate** schemas, because a call and a payment are different kinds
of object and the specification treats them as different detectors that
meet only at fusion (spec §35.1, §48):

- **Transactions** — `CanonicalColumn` in `ml/data/canonical.py`:
  provenance, user/recipient/device, amount, type, timestamp/time_index,
  sender balances, location, `is_fraud`.
- **Voice** — `VoiceCanonicalColumn`: transcript, language, audio path,
  fraud label/type, synthetic-audio flag.

### 3.1 Feature availability — the core honesty mechanism
Every adapter emits a `FeatureAvailability` record classifying each
canonical concept as `OBSERVED`, `DERIVED`, `ANONYMIZED` or `ABSENT`.
Downstream code consults this instead of inferring from nulls, because
"this dataset has no device concept" and "this row happens to be missing a
device" are different facts that must not be conflated.

Validation enforces it: a column declared `ABSENT` that contains data is a
hard **ERROR** (`fabricated_data`). That is the check that makes
"we never invent features" a tested guarantee rather than a promise.

## 4. Adapter architecture — CONFIRMED

```
External dataset -> Adapter -> validation -> canonical -> features -> model matrix
```

Dataset quirks stay inside the adapter. Examples now handled there:
PaySim's hour ordinal and its `isFlaggedFraud` leak; IEEE-CIS's
`TransactionDT` offset and card-as-user proxy; ULB's PCA block; the
TeleAntiFraud language tag.

Adapters never download. A missing file raises an error pointing here.

## 5. Label handling — CONFIRMED

"Fraud" is **not** defined identically across datasets. Each adapter
declares a `LabelDefinition` with positive/negative meaning, limitations,
and an `s40_compatible` flag.

| Dataset | Target | S40-compatible | Why |
|---|---|---|---|
| PaySim | `isFraud` | **Yes** | Mobile-money P2P transfer fraud |
| IEEE-CIS | `isFraud` | **No** | Card-not-present e-commerce; chargeback-derived |
| ULB | `Class` | **No** | 2013 credit-card fraud; PCA features |
| TeleAntiFraud | `label` | Yes (voice) | Social-engineering calls |
| S40 synthetic | `is_fraud` | Yes | Scenario ground truth |

The flag is what prevents a future training script from pooling unlike
targets into one meaningless model.

## 6. Leakage prevention — CONFIRMED

Governing rule (spec §45, §52):

```
SPLIT FIRST -> FIT PREPROCESSING ON TRAIN ONLY -> TRANSFORM VAL/TEST
```

| Risk | Mitigation |
|---|---|
| Temporal leakage | Features computed in one forward chronological pass; a row is folded into user state only *after* it is scored. There is no code path that can see a future row. |
| Target leakage | `is_fraud` is never a feature input; asserted in tests. PaySim's `isFlaggedFraud` is dropped at the adapter. |
| Decision-time unavailability | PaySim's post-settlement balance is mapped but flagged and excluded from real-time features — S40 intervenes *before* settlement. |
| Train/test contamination | `validate_no_split_contamination` checks row-id overlap. |
| User-level leakage | Same check, opt-in via `entity_column`; `grouped_split` keeps a user wholly in one partition. |
| Preprocessing on test | This module performs **no** preprocessing — split utilities only. Scaling/encoding/resampling is downstream, fitted on train alone. |
| Resampling wrong partition | `SplitResult.positive_rates()` exposes per-split balance; tests assert val/test keep the natural rate. |
| Boundary ties | Chronological boundaries advance past tied timestamps so identical instants never straddle a split. |

## 7. Synthetic data philosophy — CONFIRMED

**Purpose:** controlled scenario coverage, reproducible demos, edge cases,
and the India/UPI framing (`docs/PRODUCT_DIRECTIVES.md` §A).

**Not purpose:** evidence. Synthetic results are never real-world
validation and must never be described as representing real Indian banking
behaviour.

Properties: deterministic per seed; fabricated identifiers only
(`SYNTH-USER-*`, `SYNTH-UPI-*@synthbank`); per-user history so deviation
features mean something; scenario labels; explicit parameters.

Ten scenarios, including three that exist specifically to defeat naive
shortcuts:
- `LEGITIMATE_HIGH_VALUE` — large, known payee/device, **and a history of
  large payments** (spec §38 Scenario F). Without that history it would be
  feature-identical to `UNUSUAL_AMOUNT` with the opposite label, teaching a
  model only that large amounts are ambiguous.
- `FALSE_POSITIVE` — new payee, new device, larger amount, label 0. Feeds
  spec §26 Scenario 4 and the institution review flow.
- `NEW_RECIPIENT` / `UNUSUAL_TIME` — single weak signals, label 0. People
  pay new people at odd hours constantly.

Spec §38's prohibition on `amount > X -> fraud` labelling is enforced by a
test asserting the fraud/legitimate amount ranges overlap.

## 8. Train / validation / test — CONFIRMED

Default **70/15/15** (spec §45). **Chronological by default** for
transaction data: fraud is temporal, and a random split lets a model see
the future, producing a score that will not survive deployment.
`grouped_split` is available for the "does this generalise to unseen
users?" question. Random row-level splitting is deliberately not offered.

Class imbalance: documented per dataset by the validator, which reports
positive rate and warns below 0.1%. Any resampling belongs to **train
only** — **UNDECIDED** which technique, pending the real class
distribution of an actual downloaded dataset.

## 9. Dataset → model mapping — CONFIRMED (one item provisional)

Enforced in code (`ml/datasets/preparation.py`), not just documented:
`assert_pairing_allowed` raises on unsanctioned combinations.

| Detector | Training | Evaluation-only | Excluded |
|---|---|---|---|
| Transaction fraud | PaySim, S40 synthetic | IEEE-CIS | ULB, TeleAntiFraud |
| Behaviour anomaly | S40 synthetic | PaySim, ULB | IEEE-CIS, TeleAntiFraud |
| Device risk | *(none — rules, per spec §41)* | IEEE-CIS, S40 synthetic | PaySim, ULB |
| Voice / social-engineering | TeleAntiFraud | — | all transaction sets |

### 9.1 ⚠ UNRESOLVED — the voice language gap

**The specification (§36.3, §43) names TeleAntiFraud-28k for the voice
component but does not note that it is Chinese-language.** S40 is
India-first and must handle English/Hindi/Hinglish
(`docs/PRODUCT_DIRECTIVES.md` §A, §G). This is a genuine spec-vs-reality
conflict, escalated rather than resolved unilaterally.

- **Transfers:** the *taxonomy* of social-engineering tactics — urgency,
  authority impersonation, threat, financial request, coercion (spec §11,
  §42). These are behavioural, not language-specific.
- **Does not transfer:** any classifier trained on Chinese tokens, and any
  accuracy measured on Chinese audio. Such a number says nothing about
  Hinglish performance and must not be reported as if it did.

Options for the owner (**UNDECIDED**):
1. Use TeleAntiFraud only to derive the tactic taxonomy; build the S40
   classifier on scripted Indian-language scenarios (spec §43 already asks
   for these). Lowest risk, smallest download.
2. Train on TeleAntiFraud and evaluate on an Indian-language set that does
   not yet exist and would have to be authored. Higher cost, and the
   cross-lingual claim needs measuring before it can be believed.
3. Seek an Indian-language voice-phishing corpus. **FUTURE PHASE** —
   none identified yet.

Recommendation: option 1 for the hackathon; it keeps the demo honest and
avoids a 307-hour download whose benefit is unproven.

## 11. What Phase 3 deliberately did not do

No model training (spec §35.1's detectors are Phase 4/5). No fusion
weights (spec §12: calibrate, never invent). No accuracy claims — nothing
has been measured, so nothing is reported. No dataset downloads.
